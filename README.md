# mp4-to-gif

動画から GIF を作るローカル用フロント。**ブラウザ内で完結**する (サーバへ動画を送らない・ffmpeg も要らない)。
コマ数・出力サイズ・色数を指定して、押す前に容量の見積もりを見られる。

Discord などに貼る短い動作 GIF を、狙った容量に収めて作るための道具。

## 使う

公開版: **https://redtact-com.github.io/mp4-to-gif/** (main に入ると自動で更新される)

手元で動かす場合:

```bash
npm install
npm run dev      # http://localhost:5173
```

どちらでも変換はブラウザ内で行われ、**動画はどこにも送信されない**。
公開版で足りるので、普段は localhost を立てる必要はない。

動画をドロップ → 切り出し範囲・切り抜き・コマ数・幅を決める → **変換** → 保存。

## できること

| 項目 | 内容 |
|---|---|
| 切り出し (時間) | 開始・終了の秒指定 |
| 切り抜き (トリミング) | プレビュー上のドラッグ、または X/Y/幅/高さ の数値指定。全体 / 中央 1/2 / 左右半分のプリセット |
| コマ指定 | fps 固定 / 総コマ数固定 のどちらか |
| 出力サイズ | 幅指定 (アスペクト維持) または 幅×高さ、プリセット付き。**縦横比の基準は切り抜き後** |
| 画質 | 色数 2〜256、ディザ (Atkinson) の on/off |
| 末尾の間 | 最後のコマだけ表示を延ばす (ループの区切りを分かりやすく) |
| 容量 | 変換前の見積もり + 目標容量に収まる幅の逆算 |

対応形式はブラウザが再生できるものに準ずる (mp4 / webm など)。読めない場合は理由を画面に出す。

## 容量の見積もりについて

GIF は LZW + コマ間差分なので、容量は**中身次第で大きく振れる**。既定の係数は
密な素材 (テクスチャが詰まった画面) から逆算した上限寄りの値で、
静止が多い素材では大きく外す (実測: 画面録画 320×180 × 16 コマ で見積もり 198KB / 実測 31KB)。

そのため**1 回変換したら実測から係数を校正**し、2 回目以降はその素材に合った見積もりを出す。
表示に「前回の実測で校正済み」と出ていればその状態。動画を読み直すと係数は捨てる。

「Discord に収める」ボタンは 9MB を目標に幅を逆算する。20MB と言われていても
**16.4MB が 413 で弾かれた**実測があるので、目標は控えめに取っている。

## 開発

```bash
npm run typecheck   # tsc -b
npm test            # vitest (src/**/*.test.ts)
npm run e2e         # playwright (本番ビルドに対して実行)
npm run e2e:pages   # GitHub Pages と同じサブパス配信で読めるかの確認
npm run build
```

- `src/core/plan.ts` — 「どのコマを、どこを、どの大きさで抜くか」の純粋な計算。副作用なし・例外を投げず warnings に理由を積む
- `src/core/encode.ts` — `<video>` のシーク → canvas → [gifenc](https://github.com/mattdesl/gifenc) でエンコード
- `src/App.tsx` — UI

### E2E は素材をその場で作る

`e2e/convert.spec.ts` は canvas + MediaRecorder で**毎コマ色が変わる動画をページ内で生成**して使う。
手元の画面録画で試した時に「16 コマ中 4 コマしか中身が違わない」となり、シークが壊れているのか
素材が静止しているだけなのか判別できなかったため。素材を自分で作れば
「6 コマ抜いたら 6 種類の中身になる」を assert できる (GIF をコマ単位に切ってバイト比較している)。

外部ファイルに依存しないので CI でもそのまま回る。

切り抜きの確認も同じ考え方で、**左半分が赤・右半分が青の動画**を作って使う。
出力 GIF を canvas に描いて中央の画素を読めば「左を切り抜いたら赤・右を切り抜いたら青」を assert できる。
`drawImage` の元矩形を無視するとこれが落ちる。

### GitHub Pages

サーバ処理が無く、ffmpeg.wasm を避けたので COOP/COEP ヘッダも要らない。つまり静的配信だけで動く。
project site は `/mp4-to-gif/` 配下に置かれるので `vite.config.ts` の `base` を `GITHUB_PAGES=1` で切り替える
(dev / 通常の E2E は `/` のまま)。

`base` の設定ミスは**真っ白なページになるだけで例外もエラーも出ない**ので、`npm run e2e:pages` で確認している。
`vite preview` は base 外も index.html で拾ってしまい確認にならないため、
`scripts/serve-subpath.mjs` (Pages と同じく配下の外は 404) で配信して読み込ませている。
